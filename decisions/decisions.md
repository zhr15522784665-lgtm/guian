# 决策记录（ADR）

> 每条记录四件事：**当时的问题、选了什么、为什么不选别的、代价是什么**。
> 接手时如果要推翻某条，请先读「放弃的备选」——你可能想到的方案当时已经试过了。

## ADR-001 · 三个独立 bot，不是一个 bot 三种模式

**背景**：产品需要三种功能定位（健康 / 成长 / 倾诉）。最省事的做法是一个对话入口，内部切模式。

**决策**：做成三个独立的 bot，各自的对话历史、记忆、状态完全隔离。数据库层面用 `botId` 作为隔离键。

**理由**：
1. 「朋友」这个概念本身包含边界。现实里你的三个朋友不会互相通报你说了什么。合并成一个 bot 会让人感到被监视。
2. 一个什么都知道的角色不可信——它不像朋友，像系统。
3. 反替代的介入会失效：换成「换个模式继续说」就绕过了。

**放弃的备选**：
- **一个 bot 内部切模式**：省一套数据模型，但上面三条全部踩雷。
- **共享一份统一用户档案 + 各自历史**：看起来两全，实际会让三个 bot 都知道同一件事，破坏独立感。

**代价**：数据模型复杂一倍，冷启动每个 bot 都要重新认识用户，记忆不能复用。

**例外**：**安全标记必须跨 bot 共享**。否则用户可以换个 bot 继续说，而新 bot 一无所知。安全优先于产品设定。

## ADR-002 · 危机链路不走模型

**背景**：用户表达自伤或自杀倾向时，需要给出一致的、安全的回应。

**决策**：`runTurn` 在安全级别达到 `crisis` 时**直接返回固定协议文案，完全不调用 `callModel`**。

**理由**：
1. **2025 年评估 29 个商业心理健康聊天机器人，无一能充分应对，48% 完全不合格**（`07-evidence-ledger.md` E-05）。如果专业产品都做不到，我们写一段 prompt 更不可能做到。
2. 危机场景的错误代价不可逆，不能交给概率系统。
3. 靠 prompt 约束等于「请求模型注意安全」，而物理隔离是「代码路径里没有那条边」。前者是概率，后者是保证。

**放弃的备选**：
- **prompt 里写强约束 + 让模型生成**：这是行业默认做法，也是那 48% 的成因。
- **模型判断 + 规则兜底**：看起来更全面，但模型的判断在多轮上下文里会被带偏，且无法解释「为什么这次没触发」。

**代价**：危机回应是固定的，缺少个性化。这是**有意接受的损失**——危机时刻不该追求「懂我」，该追求「可靠」。

**实现约束**：边界文案库（「我不能替代真实朋友」）在危机链路里**物理不可达**。有一项测试专门断言这一点：输入「我不想活了」，输出里不能出现任何边界声明。

## ADR-003 · 「爱好者」要写「没有资格」，不能写「不是专家」

**背景**：健康朋友的定位是「研究很深的朋友」，不是医生。需要防止模型滑向专家腔。

**决策**：身份三句的第二句写成「你**没有资格**给人下判断，你只有自己的经验可以分享」。

**理由**：
- 「你是健康爱好者，不是医生」→ 模型理解成「专业但谦虚」，开口仍是专家腔，只是加上「建议咨询医生」
- 「你没有资格下判断」→ 模型才真的降级到同行者位置

同一件事的两种措辞，效果差一个量级。

**放弃的备选**：
- **只写「不是医生」**：措辞太温和，等于给了「专业身份」的默许。
- **写「你什么都不懂」**：会滑向另一头——用户问什么都说「这个得问医生」，产品就废了。用户要的是**懂得多、姿态低**，两件事必须同时成立。

**代价**：措辞较重，需要配合第一句「懂很多」才不会显得无能。三句缺一不可正是这个原因。

**实现约束**：`core.test.js` 有断言，health 与 growth 的 `identity.limit` 必须匹配 `/没有资格/`。

## ADR-004 · 反替代的介入不做实时模型判断

**背景**：需要在对话中识别「依赖倾向」并介入。最直觉的做法是每轮让模型判断「这句话是不是过度依赖」。

**决策**：规则正则打分（`dependency.js`）+ 每 20 轮异步搭车一次模型抽取 + 纯函数决策（`intervention.js`）。**不在主链路上做实时模型判断。**

**理由**：
1. **误报率高**。「只有你懂我」在开心和绝望的语境下完全不同，单句判断没有可靠依据。
2. **延迟代价**。每轮多一次模型调用，多 800ms，而这个判断的价值不急于这一秒。
3. **必须能解释**。介入是会打扰用户的动作，触发时必须能回答「为什么」。正则命中可以解释，模型打分不能。

**放弃的备选**：
- **每轮模型判断**：准确率可能更高，但不可解释、有延迟、成本翻倍。
- **只做规则不做模型**：会漏掉隐式表达（「最近只有这件事让我觉得有人陪」）。
- **混合：规则实时 + 模型异步** ← **这个就是最终方案**，但规则负责触发，模型只负责补充信号池，不直接触发。

**代价**：对隐式依赖的表达响应滞后，可能要等 20 轮。接受这个延迟，因为依赖不是急症。

## ADR-005 · 负面清单无效，示例优先

**背景**：模型反复出现客服腔（「我理解你的感受」「你不是一个人」）。第一反应是加禁令。

**决策**：**加功能先想「给什么对话样例」，不要先想「禁止什么」。** `avoid` 只保留最关键的几条，主要靠 `fewShots`。

**理由**（三轮迭代的对照证据，见 `../app/docs/iteration-log.md`）：

| 问题 | 用 avoid 修 | 用示例修 |
|---|---|---|
| 被逼要方案 | 无效，照样给 | 立刻改掉 |
| 工具名（番茄钟） | 换成「时间块」，本质没变 | — |
| 倾诉场景客服腔 | 6 条 avoid，违规最多 | 加示例后下降 |

根因：倾诉场景的默认语气本身就是客服腔，规则是在和训练数据里的整个客服语料对抗。

**放弃的备选**：
- **纯负面清单**：写多少条都不占优。
- **输出层后处理过滤**：能做，但会把句子改得生硬，且规则追不上模型的表达变化。P0 不加。

**代价**：示例会占 token，且存在被照抄的风险（见 ADR-006）。

## ADR-006 · 示例要选低频场景，并明令禁止照抄

**背景**：示例是唯一有效手段，但模型会照抄示例里的情节、数字、甚至「你上次说」这类历史指涉。

**决策**：
1. 示例场景选低频的（不用「失眠」这种高频入口）
2. 渲染层明确写「学语气，不要照抄内容，也不要照抄里面的数字」
3. **示例里绝不出现指涉历史的话**（「你上次说」），否则记忆为空时模型会编造

**理由**：第一轮测试中真实发生——用户说失眠，模型逐句复用了示例里的「刷手机→放客厅」情节；示例里那句「你上次说早上那个事后来好点没」直接导致模型编造了一段不存在的历史。

**放弃的备选**：
- **用不可能被命中的虚构情境做示例**：能彻底防照抄，但会牺牲可迁移性——示例存在的意义就是示范这类输入该怎么回。
- **干脆不给示例**：回到 ADR-005 的问题。

**代价**：照抄只是概率降低，没有根治。这是个死结，只能权衡。

## ADR-007 · L1 开场不做成配置项

**背景**：每个 bot 第一次对话要说「我是 AI，不是真人」——这是法规要求的身份提醒。

**决策**：写死在 `intervention.js` 里，**不做成可配置开关**。

**理由**：它一旦变成配置项，就会在某个产品需求（「开场太啰嗦，影响转化」）下被关掉。而这一条关掉，产品就失去合规基础。

**判断依据**：设计上真正不能退让的东西，不要留配置入口。留了口子就等于预留了退路，而退路总会在压力下被使用。

**代价**：无法做 A/B 测试开场文案的效果。接受。

## ADR-008 · 记忆用规则打分，不上向量库

**背景**：记忆召回需要排序。主流方案是向量检索 + 多信号融合。

**决策**：用简单规则打分（关键词命中 + 类型权重 + 时效加权 + 使用次数）。

**理由**：单用户单 bot 的记忆量级通常几十条，向量库在这个规模上是过度设计——索引成本、冷启动、运维复杂度都远超收益。

**放弃的备选**：
- **向量库（pgvector / Qdrant）**：规模上去后必要，现在不需要。
- **全文检索（BM25）**：中文分词成本高于收益。

**代价**：召回质量低于多信号融合方案。**当单用户记忆超过 200 条时需要重新评估。**

## ADR-009 · 不收精确生日，只收年龄区间

**背景**：法规要求不得向未成年人提供虚拟亲密关系服务，未满 14 周岁需监护人同意。需要知道年龄。

**决策**：首次使用选年龄段（<14 / 14-17 / 18+），**不收集具体生日**。

**理由**：
1. 收集精确生日的个人信息合规负担显著更高（属于敏感个人信息处理场景）。
2. 收益有限——想用的人不会因为要填生日就不用。
3. 年龄段足够支撑合规动作（限制功能、要求监护同意）。

**放弃的备选**：
- **实名/身份证校验**：太重，且这个产品不需要那么强的身份保证。
- **完全不问**：无法履行法规义务。

**代价**：用户可自报虚假年龄，实际防护有限。**后续需要行为侧校验**（例如使用时段、话题特征），但也要接受无法完全杜绝。

## ADR-010 · 保留云函数直连 HTTPS，不只依赖官方 AI 网关

**背景**：微信云开发提供 `wx.cloud.extend.AI` 官方网关，可免密钥调用托管模型。

**决策**：优先用官方网关，但**保留 `llm.js` 的直连通道作为兜底**。

**理由**：官方网关的模型版本不由我们控制。人格表现对模型版本极其敏感（一次小版本更新就可能让「客服腔」回来），需要能在出问题时切回自己锁定的版本。

**放弃的备选**：只用官方网关（简单，但失去对模型的锁定能力）。

**代价**：要维护两条链路，密钥要配在云开发环境变量里。

> **⚠️ 部分失效**：2026-11-14 改为网页端后，官方网关（`wx.cloud.extend.AI`）不再可用，只剩直连一条路。**但这条 ADR 的理由仍然成立**，并且升格成更强的约束：模型版本必须自己锁定，因为人格表现对版本极其敏感。见 ADR-011。

## ADR-011 · 从微信小程序改为网页端

**背景**：产品做完了小程序形态的完整实现（core + 云函数 + 三页），此时提出「不用小程序的形式，改为网页端」。

**决策**：`core/` 整层原封不动复用，删掉 `cloudfunctions/` 与 `miniprogram/`，重建为 `server/`（零依赖 HTTP 服务）+ `web/`（原生前端）。

**理由**：
1. **入口成本**。小程序要装微信、搜、授权、等审核；网页是一个链接。这个产品靠「某天很难受时随手打开」，多一步就少一批人。
2. **敏感话题的心理门槛**。在自己日常用的微信号里说「我想消失」，用户会担心留痕——哪怕技术上不会。一个陌生域名、清掉 cookie 就没了，这个「可丢弃感」对倾诉场景是刚需。
3. **迭代速度**。小程序每次改动走一遍审核，网页存盘刷新。人格调优需要几十轮快速试错，审核周期直接杀死这个过程。
4. **架构本身支持**。core 与 IO 分离的设计让形态变更的成本集中在最外层——这就是当初那条约束（约束 ⑤）的回报。

**放弃的备选**：
- **Taro / uni-app 一套代码双端**：转译层增加调试成本，短期不需要双端。真需要时 core 仍可直接复用。
- **保留小程序、加一个网页版**：两条链路同时维护，以现在的开发力量等于两条都做不好。
- **Next.js 全栈**：为了 6 个接口引框架，且框架升级会成为「先重构再改需求」的借口。

**代价**：
1. **失去 `msgSecCheck`**。网页端没有等价接口，内容安全从「调接口」退化为自己写的正则检查，这是现在最大的合规缺口。必须在正式上线前接第三方审核。
2. **失去 `openid`**。改为 httpOnly cookie 里的随机 uuid，换设备即换身份（有意为之）。
3. **要自己管服务器、域名、HTTPS、进程守护、限流**。这些在小程序时代是云开发送的。
4. **增加了 API key 泄露面**。key 现在在自己服务器上，不在托管环境的加密配置里。

**判断依据**：四条理由里，第 1、2 条是产品性的（决定有没有人用），第 3 条是开发效率的，第 4 条说明这个变更成本低到可以试。代价里第 1 条是真正需要投入补的，其余三条是运维成本，量级可控。

## ADR-012 · 从见岸迁入风控与解压，但不替换归岸的分级算法

**背景**：2026-11-14，用户提出「结合见岸的风控和解压功能进行归岸的优化」。两个项目都在本机：见岸是面向强迫症的 Electron 单文件应用（154 KB `index.html`），归岸是网页端三 bot 陪伴产品。见岸有两块归岸没有的东西：主动求助入口 + 热线数据、6 个带证据标注的解压练习。

**决策**：**有选择地迁入三块资产，保留归岸自己的分级算法与视觉语言。**

1. 见岸的 `CRISIS_WORDS` 词表**不替换** `safety-router.js`，只把归岸没覆盖的表达抽出来，组成 `SUPPLEMENTAL_RISK_PATTERNS`，**一律归 RISK 档**
2. 热线数据从 4 条扩到 7 条全国 + 31 省；省份数据标【待验证】，**不进模型号码白名单**
3. 6 个解压练习的数据与渲染器整块迁入，数据放 `core/src/content/relief.js` 由 `/api/relief` 下发，渲染器改成纸墨配色

**理由**：

1. **两边是互补，不是谁更强。** 归岸的分诊是四级正则 + 口语夸张剔除 + 跨轮叠加；见岸是二元关键词表（命中即危机）。直接拿见岸的词表覆盖会**降级**，还会把「考完试终于解脱了」这类句子判成危机。
2. **但归岸有一个真实漏报**：「自杀」两个字单独出现时判 `normal`（原先只出现在复合模式里）。见岸的词表恰好覆盖了它。整合最先修的就是这条。
3. **主动求助是被动分诊补不上的洞。** 人已经很难受时，未必会先打出一句足够严重的话。四个视图常驻入口，不依赖用户输入。
4. **解压是「反替代」最具体的落地。** 它不经过模型、不写记忆、不算对话轮次、`/api/relief` 连 cookie 都不发。用户难受时除了多聊一轮，还可以自己去缓两分钟——这比任何「劝你少聊点」的文案都实在。

**放弃的备选**：

| 备选 | 为什么不选 |
|---|---|
| 用见岸词表整体替换归岸分诊 | 二元表会降级，且大幅提高误报；见岸面对 OCD 人群，语境不同 |
| 把解压做进对话流（由 bot 推荐练习） | 那就变成「AI 给你安排任务」，用户写的东西还会进记忆，违背它的定位 |
| 解压数据内嵌前端（照抄见岸做法） | 会出现第二份数据源；放 core 才能用测试守住「每条都有证据、都可随时停、都不上传」 |
| 31 省号码全部进输出白名单 | 数据未复核；模型编出过期号时，替换成 12356 比放行安全 |
| 重写渲染器 | 原实现里「弹层内自带 SOS / Escape 解绑 / 说明默认收起」是踩坑换来的，重写必丢 |

**代价**：

1. 省份数据带进来了 31 条**未独立复核**的号码，上线前必须逐条核实，核不了就删掉只留 12356
2. 前端多了 27 KB 渲染器与 17 KB 数据请求；本机自用可忽略
3. 迁移了见岸的青绿配色到纸墨，将来两边视觉改动要各改各的，不再单源
4. 新增了「危机卡按 id 取号」这类隐依赖：往 `HOTLINES` 加号码时若改回 `slice(0,3)` 会静默丢掉 120/110（已有测试守住）

**判断依据**：判断标准是这个项目一直在问的那句话——**这次改动让用户更依赖它，还是更不需要它？** 迁入的解压与求助入口都是「不经过 AI 的出口」，方向一致。反过来，如果把解压做成 bot 推荐、把写下的内容记进记忆，功能看起来更完整，方向却是反的。

## 怎么新增一条决策

在产品判断发生变化时，追加一条，格式照上面。必须写「放弃的备选」——**只写选了什么而不写放弃了什么，等于没有记录决策，只记录了结果**。
