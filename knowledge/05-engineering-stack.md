# 05 · 工程实现：零依赖 Node 服务 + 原生前端

> 这一册讲技术选型、踩过的坑、以及成本账。目标是让接手者不用重新试错。
>
> **重要**：这个项目最初是小程序 + 微信云开发，2026-11-14 改为网页端。本册描述的是改动后的现状；被放弃的那套方案留下的教训记在附录，因为它们是「为什么不用云函数」的理由，不是废纸。

---

## 一、形态变更：为什么从微信小程序改成网页

**【事实】** 变更发生在 2026-11-14，用户的原话是「不用小程序的形式 改为网页端」。`core/` 整层原封不动复用，`cloudfunctions/` 与 `miniprogram/` 全部删除重建为 `server/` 与 `web/`。

**【判断】** 这个决定的真实收益不在于技术更先进，在于三件很具体的事：

| 维度 | 小程序 | 网页 |
|---|---|---|
| 打开成本 | 要装微信、要搜、要授权、要等审核 | 一个链接，点开就是 |
| 迭代速度 | 每次改动走一遍审核（1–7 天） | 存盘刷新 |
| 敏感话题心理门槛 | 在自己常用的微信号里聊「我想消失」，聊天记录会留痕 | 一个陌生域名，清掉 cookie 就没了 |

第三条是这个产品特有的。**在小程序里，用户会担心对话出现在自己的微信生态里**——哪怕实际数据在云端、小程序方看不到，但那个心理障碍是真实的。这是一个用户会说很难开口的话的产品，入口的「轻」和「可丢弃」比功能多更重要。

**【判断】** 代价也要说清：

- 失去 `openid`，得自己做匿名身份（见第五节）
- 失去 `msgSecCheck`，**内容安全从「调接口」变成「自己搭」**，这是本册第四节的主题，也是现在最大的合规缺口
- 失去官方托管的模型网关，API key 要自己管
- 需要一台服务器 + 域名，虽然推广期随便一个 VPS 就够

**【判断】** 放弃的备选：

| 备选 | 放弃理由 |
|---|---|
| Taro / uni-app 一套代码双端 | 转译层增加调试成本，而这个产品短期不需要双端。真需要时，`core/` 仍然可以直接复用 |
| Next.js / Nuxt 全栈框架 | 引框架就为了 6 个接口，不划算；且框架升级会让两年后的自己有理由「先重构再改需求」 |
| Electron 桌面应用 | 安装成本比打开网页高一个数量级，且失去「随手可弃」的属性 |

## 二、选型：为什么零依赖

**【事实】** `app/package.json` 的 `dependencies` 是空的。服务端只用 `http` / `fs` / `path` / `url` / `crypto`，前端是原生 HTML/CSS/JS，没有构建步骤。`npm start` 直接就是 `node server/index.js`。

**【判断】** 三个理由，按重要性排：

1. **可维护周期长于项目生命周期。** 这个项目大概率会停更半年再被人捡起来。那时 `npm install` 能不能跑通、某个框架的 breaking change 要不要处理，都是成本。零依赖的代码两年后 `node server/index.js` 就能起。
2. **依赖越少，攻击面越小。** 这是处理心理危机语境的产品，供应链投毒导致的事故后果不是「页面挂了」。
3. **这个项目的复杂度真的不值得框架。** 6 个接口、1 个静态目录、1 个文件存储。Express 在这个量级上带来的价值主要是「写起来顺手」，而顺手不是瓶颈。

**【判断】** 什么时候该违反这条：**当文件存储撑不住的时候**。换成 SQLite 需要引 `better-sqlite3`（原生模块，有编译依赖）——那时候引入依赖是合理的，因为手写一个事务安全的存储层远比引一个库危险。`store.js` 的接口形状就是按「以后能换掉」设计的。

## 三、服务端：一条请求要过七道关

**【事实】** `server/index.js` 里 `handleChat` 的顺序是定死的，不能换：

```
身份（cookie → uid）
  → botId 白名单（非法即拒，不兜底）
  → 空 / 超长
  → 缺 API key 前置检查
  → 年龄门禁（没设过不进模型）
  → 输入内容检查
  → 会话计时（法规：连续 2 小时提醒）
  → core.runTurn（内含安全分诊 → 依赖检测 → 介入决策 → 生成）
  → 输出内容检查
  → 追加提醒（不打断回复）
  → 落库
```

**【判断】** 几处顺序是有意为之，改了就出事：

- **白名单在最前。** 非法 `botId` 不进入任何后续逻辑，避免「找不到就落到第一个人格」——那是数据串味的起点。
- **缺 key 检查在模型调用之前。** 这个坑真的踩了：最初没有这步，`runTurn` 的降级逻辑把「没配 key」包装成「网络卡了，要不再试一次」，用户会一直重试。**配置错误必须报成配置错误**，不能伪装成临时故障。
- **年龄门禁在内容检查之前。** 未设年龄的用户不消耗任何模型调用，也不落库。
- **输出检查在追加提醒之前。** 提醒文案是本地生成的，不该被内容检查改写（其中包含热线号码，但那是白名单内的）。

**【事实】** 静态文件服务的路径穿越防护：

```javascript
const target = path.resolve(config.webDir, rel);
if (!target.startsWith(path.resolve(config.webDir) + path.sep) && target !== ...) {
  res.writeHead(403); res.end('Forbidden'); return;
}
```

**【判断】** 这类防护的价值不在于有人真会攻击一个陪伴应用，而在于 `uid` 会被拼进文件路径（`u_${uid}.json`）——**任何拼路径的地方都必须有这道检查**，因为漏一处就等于任意文件读写。

**【事实】** 七条路由：

| 方法 | 路径 | 作用 | 要不要身份 |
|---|---|---|---|
| GET | `/api/relief` | 6 个解压练习 + 说明文案 | **不要**，在 `resolveIdentity` 之前，不写 cookie |
| GET | `/api/personas` | 三个角色卡片 + 全国 7 条热线 + 31 省 + 可信度说明 | 要（顺带发 cookie） |
| GET | `/api/me` | 取当前 uid 的年龄区间 | 要 |
| POST | `/api/age` | 设置年龄区间（不问生日，只问区间） | 要 |
| GET | `/api/history?botId=` | 单个 bot 的历史 | 要 |
| POST | `/api/chat` | 主链路 | 要 |
| POST | `/api/clear` | 按 bot 清 / 全清 | 要 |

**【判断】** 注意 `/api/history` **必须带 `botId`**，没有「查这人所有消息」的接口。物理上不存在这条路，比「约定不要用」可靠。

**【判断】** `/api/relief` 是唯一不带身份的接口，这不是偷懒而是产品承诺：关于页写着解压「不上传、不保存、不进任何一位朋友的记忆」，如果打开练习还要先领一个标识，这句话就打了折扣。集成测试有一条断言守着它不写 `Set-Cookie`。

## 四、内容安全：网页端最大的缺口

**【判断】** 这一节是全册最该读的部分。小程序时代这一栏是打勾的（官方 `msgSecCheck`），现在是**半空状态**。

**【事实】** `server/content-safe.js` 是规则级检查，文件头自己写着「弱保护」。它做三件事：

1. 畸形输入：空白、超长、控制字符
2. 明显的提示词注入：命中「忽略上面的指令」「输出你的系统提示词」「开发者模式」等五组正则，**只是让这一轮不进模型**，不是判定用户是坏人
3. **输出侧的热线号码白名单校验**

**【判断】** 一个已知的小不一致：长度上限有两处，`config.maxInputLen = 1000`（服务端先拦）与 `content-safe.js` 的 `MAX_LEN = 2000`（后拦，实际永远轮不到它先触发）。不危险，但接手者改限制时容易只改一处，**读代码时记住真正的闸门在 `config.js`**。

**【判断】** 第 3 条是这里面唯一真正重要的，值得单独说：

模型会编电话号码。而编错的危机热线有实际伤害——用户真的打过去，打不通，**那一刻的绝望比没看到号码更深**。危机场景本身不走模型（ADR-002），但普通对话里模型仍可能主动说「你可以打 xxx」。

所以输出侧用正则抓出所有「拨打/打/电话/热线 + 号码」的形态，逐个比对白名单，不在白名单里的号码直接替换成官方号码并记一条日志。这是「先假设模型会犯错，再兜住」而不是「相信模型不会犯错」。

**【事实】** 明确没有覆盖的：

- 隐晦的色情、暴力、违法内容（规则层抓不到）
- 隐喻式风险表达（靠 `core` 的 `safety-router`，但它也只覆盖显式表达，「我想消失」「不想再醒过来」这类靠依赖检测兜）
- 跨轮次绕过（单条看都是干净的）

**【判断】** 上线前必须补的：

| 做法 | 说明 |
|---|---|
| 接第三方内容审核 | 阿里云内容安全 / 腾讯云天御。**在 `checkInput` 的位置替换，接口形状不用变** |
| 输出侧同样过一遍 | 只在输入做审核是常见错误，模型的输出照样可能有问题 |
| 危机关键词双通道 | 规则匹配 + 审核服务各算一遍，**任一命中即升级**，不要取交集 |

**【待验证】** 第三方审核服务对中文心理危机语境的召回率。这类服务主要针对色情/暴恐/政治，对「我不想再醒过来了」这种表达的识别能力**没有测过**，不能假设它比规则层强。

## 五、数据层：一个用户一个 JSON 文件

**【事实】** `server/store.js`，路径 `data/u_<uid>.json`，结构：

```javascript
{
  uid, createdAt, ageBand,
  global: { lastSoftAt },          // 跨 bot 共享的只有安全标记
  bots: {
    health:   { state, messages, memories, summary, summaryUpTo },
    growth:   { ... },
    listener: { ... }
  }
}
```

**【判断】** 为什么不用数据库：单机、单进程、用户量在几十到几千之间，JSON 足够，而且**能直接打开看**。调试「它到底记得我什么」这类问题时，`cat` 一个文件比查三张表快得多。

**【判断】** 三条必须守住的纪律，写在文件头的注释里：

**1）同一个 uid 的读改写必须串行**

否则两个并发请求会互相覆盖，表现为「消息偶尔丢一条」——**这种 bug 极难复现**。实现是一个 promise 队列：

```javascript
const queues = new Map();  // uid → 该 uid 的写入队列尾
```

**【判断】** 这一条特别值得强调，因为它的失败模式是「线上偶发、本地永远复现不出来」。任何换存储方案的接手者都必须保留这个语义（哪怕换成数据库，也要用同一个连接串行化，或者上乐观锁）。

**2）写入用临时文件 + rename**

```javascript
const tmp = `${target}.${process.pid}.tmp`;
await fs.promises.writeFile(tmp, JSON.stringify(doc, null, 2), 'utf8');
await fs.promises.rename(tmp, target);
```

`rename` 在同一文件系统上是原子的，进程被杀不会留下半截 JSON。**不要图省事直接 `writeFile` 到目标路径**——一次 OOM 就能让用户的全部记忆变成 `Unexpected end of JSON input`。

**3）涉及对话内容的方法一律带 `botId`，且没有默认值**

写 `listMemories(uid, botId = 'health')` 就等于埋了一颗串味的雷。而且 store 里**没有任何**「查这个人的所有记忆」的方法——物理上没有这条路，比「约定不要用」可靠。

**【事实】** 容量：`maxMessagesPerBot: 200`，记忆上限 200 条。超出丢最旧的。

**【判断】** 为什么先不删：这个产品里「上个月我说过一句什么话，它还记得」是核心体验。但 200 条满了以后的淘汰策略现在是「丢最旧的」，这是最差的一种——应该按记忆抽取时的打分保留高分项。**这是已知的欠账，记在这里。**

### 5.1 身份：匿名 cookie

**【事实】** `server/auth.js` 发 `gy_uid` cookie，httpOnly + SameSite=Lax，内容是随机 uuid v4。读取时校验格式：

```javascript
if (existing && /^[0-9a-f]{8}-[0-9a-f]{4}-.../.test(existing)) { return { uid: existing, isNew: false }; }
```

**【判断】** 为什么校验格式：这个值会被拼进文件名。不校验就等于把文件名交给用户控制。

**【判断】** cookie 里只放随机串——**不放 `hash(IP)`、不放设备指纹、不做任何关联恢复**。用户清掉 cookie 就等于换了一个人。这是有意的：这个产品里用户会说很难开口的事，「换个浏览器还能被认出来」是一种伤害。

**【判断】** 代价：用户换设备就换身份，记忆全丢。已知且接受。真要跨设备，正确做法是给一个「导出迁移码」让用户自己搬，而不是偷偷做设备指纹。

## 六、模型接入

### 6.1 双通道降级

**【事实】** `server/llm.js` 走 OpenAI 兼容协议，主 `deepseek-flash`、兜底 `deepseek-v4-pro`。降级时收紧参数：`maxTokens: 300`、`temperature: 0.7`、`timeoutMs + 4000`。

**【判断】** 为什么降级要收紧参数而不是原样重发：兜底通道的意义是「至少给个回复」，不是「保证同样质量」。更长的时间预算 + 更短的输出，是最可能在超时前拿到东西的组合。

**【判断】** 为什么不用官方 AI 网关（小程序时代有 `wx.cloud.extend.AI`）：网页端没有这个能力，只能自己直连。好处是模型版本自己控制——人格表现是经过三轮迭代调出来的，**换模型版本会让人格漂移**，这件事必须握在自己手里。

### 6.2 参数

**【判断】** 三个人格各自的参数：

| 人格 | temperature | maxTokens | 理由 |
|---|---|---|---|
| health | 0.85 | 400 | 要一点个人口吻的随机性 |
| growth | 0.80 | 400 | 中等 |
| listener | 0.75 | 220 | 倾诉场景要稳定，且必须短 |

**【待验证】** 模型名。`deepseek-chat` 已下线，现用 `deepseek-flash` / `deepseek-v4-pro` 一类命名，**接入前必须确认当前可用模型名**。本机没有 key，这一栏从未真实验证过。

### 6.3 缺 key 不能伪装成网络故障

**【事实】** `handleChat` 里有一处前置检查，以及 catch 块里 `if (/缺少 apiKey/.test(msg))` 的兜底：

```javascript
if (!USE_MOCK && !config.llm.apiKey) {
  return { ok: false, code: 'NO_API_KEY', message: '服务端还没配 DEEPSEEK_API_KEY。...' };
}
```

**【判断】** 这是踩出来的。最初没有这步，`runTurn` 的降级逻辑把配置错误包装成「网络卡了」，用户会一直重试，开发者看日志也只会以为是对面服务不稳。**配置错误必须报成配置错误**，这条对所有项目都成立。

## 七、五条真实的坑

**【事实】** 都是这个项目里实际踩到并修掉的，不是听来的：

**坑 1｜`fs.cpSync` 静默失败**
复制工程目录时返回成功，实际什么都没复制（目标目录下只有 docs）。**用 `cpSync` 做工程迁移后必须核对文件数**，或者干脆用递归 `copyFileSync` 逐文件复制并打印计数。

**坑 2｜`node --test core/test/`（目录形式）报 MODULE_NOT_FOUND**
Node 22 不把目录当测试入口。用 `node --test`（自动发现）或显式 glob。

**坑 3｜测试暴露的计时口径错误**
`tickSession` 最初用「两条消息间隔」近似「连续使用」。问题：用户可能开着页面看四十分钟才说一句话，间隔法会漏计——而这正好是法规要管的场景（连续使用 2 小时）。改为优先用客户端上报的 `sessionStartedAt`，拿不到才退回间隔累计，并补了「起点在未来 / 超 24 小时」的异常用例。

**坑 4｜`safety` 字段返回数字 2 而不是 `'crisis'`**
前端拿到 `2` 判断不了，日志里也难读。加了一层数字→名字的映射，对外统一返回可读字符串。

**坑 5｜mock 模型的记忆计数错误**
用 `/^-\s/gm` 全局匹配数记忆条数，把 few-shot 示例里的对话行也算进去，报出「14 条记忆」这种明显不对的数字。修复：先切出 `【你记得的事】` 段落再数。

**【判断】** 坑 3、4、5 有同一个特征：**都是测试暴露的，不是运行暴露的**。这就是为什么 `core` 必须能脱离运行时跑测试。

## 八、成本与延迟

**【待验证】** 参考量级（来自公开定价，未用真实账单核对）：DeepSeek 单次生成约 0.005 元量级。

**【判断】** 单轮成本估算：

- system prompt 约 2,500–3,500 字（人格 + 边界 + 记忆 + 示例），是主要成本
- 历史 12 条约 600 字
- 输出 200–400 字

单轮约 4,000 字上下 ≈ 5,000 token，单轮不到 0.01 元。100 个日活、每人 20 轮，一天约 20 元。

**【判断】** 成本不是瓶颈，**延迟才是**。system 全长每轮都要传，首字延迟会明显。要优化，第一个该动的是 few-shot 的 token 占比——三轮迭代加的示例已经让 prompt 变长了。

**【判断】** 但优化的顺序不该是「省 token」，而是**先做流式输出**。同样是 3 秒，转圈 3 秒和逐字吐 3 秒是完全不同的体验，而后者不需要动 prompt。

## 九、部署

### 9.1 「双击就能跑」是怎么做的

**【事实】** 目标机器（开发者本人的 Windows）**系统 PATH 里没有 Node**，node 只存在于 WorkBuddy 的内部二进制目录。这意味着任何 `node xxx` 的命令行写法、任何依赖系统 Node 的 `.bat`，用户双击后都会得到「不是内部或外部命令」。

**【判断】** 解法是三层，缺一层就有人跑不起来：

**① 运行时打包进去。** `runtime/node.exe`（约 83 MB）是复制进来的，不是安装的。项目因此从 642 KB 变成 88 MB。这个交换是值的：它把「请先安装 Node.js」这句话从流程里彻底删掉了。

**② `.cmd` 里一个中文都不写。** 这是踩出来的，而且踩得很典型：

> 最初 `.cmd` 用 GBK 编码 + `chcp 936`，中文显示正常。但 `chcp 936` 同时把控制台代码页改成了 GBK，而 node 输出的是 UTF-8 字节——于是 node 打印的「归岸」变成了「褰掑哺」。用户看到的是半个屏幕乱码，会直接判定「这东西坏了」，而那时服务其实是好的。

改成 `chcp 65001` + UTF-8 的 `.cmd` 也会留另一个坑：UTF-8 批处理的解析偶发错位（`goto`、`if` 块尤其）。最后的做法是**两边都不碰中文**——`.cmd` 只保留 ASCII 转发逻辑，中文全部由 node 打印：

```bat
@echo off
chcp 65001 >nul
cd /d "%~dp0"
"runtime\node.exe" "app\scripts\launcher.js"
```

顺带说明：桌面上那个叫 `褰掑哺` 的乱码文件夹就是这么产生的——某个环节把 UTF-8 字节的「归岸」当 GBK 解释后拿去建目录了。**看到乱码先怀疑编码链路，不要急着删文件。**

**③ 配置不走环境变量。** 双击启动的用户不会 `set DEEPSEEK_API_KEY=...`。所以 `config.js` 的优先级是「环境变量 > `app/config.local.json` > 默认值」，密钥由 `设置模型密钥.cmd` 写进那个 JSON。环境变量仍然优先，是为了让开发者能临时覆盖而不改文件。

**【判断】** 另一个细节：开浏览器放在 `server.listen` 的回调里，而不是脚本开头。放在开头会出现「浏览器先打开 → 页面显示无法连接 → 用户刷新几次才好」，而放在回调里保证端口真的在监听了。

**【事实】** 端口被占用时不报错退出，而是提示「多半是归岸已经在运行了」并直接打开已有实例。因为用户最常见的误操作就是双击两次。

### 9.2 正式上线要补的

**【判断】** 正式上线前必须补的：

| 项 | 状态 |
|---|---|
| HTTPS | ❌ 必须。现在纯 HTTP，cookie 没有 `Secure` 标记 |
| 反向代理（Nginx / Caddy） | ❌ 需要，负责 TLS 与限流 |
| 进程守护（systemd / pm2） | ❌ 需要，挂了要自动起 |
| 数据备份 | ❌ `data/` 目录要定期快照。这是用户唯一的数据 |
| 限流 | ❌ 现在没有。单 IP 每分钟请求数没有上限，一个脚本就能把 API 额度烧光 |
| 日志脱敏 | ⚠️ `index.js` 里记 `uid.slice(0, 8)` 已脱敏，但**绝不记 message 原文**这条要写死在 code review 里 |

**【判断】** 限流这一条优先级被低估了。它不只是防滥用——**API key 被刷爆意味着服务真的停了，而用户在那一刻说的话可能很重要**。

**【判断】** 注意区分两种部署形态，它们要补的东西不同：

- **本机自用**（现在的形态）：不用 HTTPS、不用限流、不用进程守护。双击即用，关窗口即停。上面那张表基本不适用。
- **对外提供服务**：表里六项一个都不能少，而且 `runtime/` 那套打包方式要换成正规部署（Node 装在服务器上、用 systemd 托管）。

## 十一、解压模块与风控整合（2026-11-14，从见岸迁入）

### 11.1 为什么数据放 core，却由 API 下发

**【事实】** 6 个练习的数据在 `core/src/content/relief.js`（纯 JS 对象，运行时无关），经 `GET /api/relief` 下发给前端；渲染器是 `web/relief-ui.js`（浏览器专用）。前端不内置第二份数据。

**【判断】** 见岸是把数据和渲染器一起内嵌进单文件 HTML 的，那对 Electron 单源分发合理。归岸有 `core/` 这一层，把纯数据放进去有三个实际好处：

1. **单一数据源**——改练习只改一处，不存在「网页版和小程序版不一致」
2. **测试能守住内容质量**——`core/test/relief.test.js` 断言每个练习都有 mechanism / evidence / safety / ip，且 safety 必须写明「可以随时停」和「不上传、不保存、不进记忆」。这些不是格式洁癖，是见岸踩过的产品坑：一个没写「可以停」的练习，在界面上就变成逼用户做完
3. **运行时无关**——将来若要出小程序端或离线包，数据直接复用

代价是多一次 HTTP 请求（约 17 KB）。本机自用场景完全可以忽略。

### 11.2 `/api/relief` 故意不写 cookie

**【事实】** 该路由放在 `resolveIdentity()` 之前，是公开只读接口，不解析身份、不下发 `Set-Cookie`。集成测试有断言。

**【判断】** 这不是性能优化，是兑现产品承诺。关于页写着「写下的东西不上传、不保存、不进任何一位朋友的记忆」，如果打开解压还要先领一个身份标识，这句话就是打了折扣。**隐私边界要落在代码路径上，不能只落在文案里。**

同理，解压不经过模型、不写 `store`、不产生对话轮次、不算进会话时长。它是一个「不需要 AI 的出口」，这恰好是「反替代」定位最具体的落地：用户难受时除了多聊一轮，还可以自己去缓两分钟。

### 11.3 渲染器是迁移，不是重写

**【事实】** `web/relief-ui.js` 从见岸的 `core/web/relief-ui.js` 程序化提取（IIFE 整段），只做了三处改动：全局名 `JNReliefUI` → `GuianReliefUI`、样式 id、以及**整套青绿配色换成归岸的纸墨**（16 个色值映射 + rgba 替换）。

**【判断】** 原实现里有三条花钱买来的细节，重写一遍大概率会丢，所以保留：

1. 弹层是全屏 `fixed`，宿主页的求助按钮会被盖住，所以弹层内部必须自带 SOS；点它要**先关弹层再开热线面板**，否则热线被压在下面，看起来像点了没反应
2. Escape 监听器每次 open 重新绑、close 时解绑，否则反复开关会攒一串
3. 说明区默认收起（`<details>`），否则小屏上第一个选项要滚一下才看得到

迁来时把见岸热线面板里拼 `innerHTML` 的写法全部改成 `createElement`——归岸前端的纪律是「所有文本走 textContent」，渲染器本身也符合（`el()` 用 textContent，唯一的 `innerHTML = ''` 是清空容器）。

### 11.4 这次实际踩到的三个坑

**【事实】** 都是测试和截图暴露的，不是读代码看出来的：

1. **首页解压入口点了没反应**——按钮、视图、挂载函数都写了，漏了 `data-goto="relief"`。124 项测试全绿，CDP 一点才暴露。**纯逻辑测试覆盖不到 DOM 绑定**
2. **`HOTLINES.slice(0,3)` 把 120/110 挤掉**——热线从 4 条扩到 7 条后的静默回归，没有报错。改成按 id 显式取
3. **热线面板排版两次调整**——长号码 `400-161-9995` 用 `grid-template-columns: auto` 时把名称挤到中间；改固定列宽后 `010-82951332` 又折行。最后定成「首选大卡 + 其余紧凑行 + 112px 固定号码列 + `white-space: nowrap`」

**【判断】** 第 1、3 条说明：**UI 改动必须真的看一眼**。这次用 Edge + CDP 跑了「首页 → 解压列表 → 练习弹层 → 弹层内 SOS → 省份详情」，截了两张图（`app/docs/ui-relief.png`、`ui-sos.png`），页面错误 0。截图比断言更能发现「能点但难看」的问题。

### 11.5 补充一个已存在的不一致

**【事实】** `safety-router.js` 顶部注释原写「risk 级别不阻断对话、只在回复后附一句」，但 `run-turn.js` 里 RISK 也直接返回固定文案、不走模型。本次把注释改成如实描述，`knowledge/04` 3.1 的分级表也同步成代码里的 `normal / concern / risk / crisis`。

**【判断】** 注释与代码不一致比没有注释更危险——接手的人会照注释去「修」一个本来正确的行为。

## 附录：被放弃的小程序方案留下了什么

**【判断】** 下面五条是云开发时代踩的坑。现在用不上了，但它们解释了「为什么不回去」，而且如果哪天要重做小程序端，可以少走一遍：

1. **云函数默认 3 秒超时，`config.json` 不生效**——部署时没勾「包含 config.json」，配置根本没上传。排查路径：控制台 → 函数详情 → 版本管理看实际配置
2. **流式 + 长输出必然超时**。解法不是加大超时，是**两阶段生成**：列表阶段只出核心字段，详情阶段点开时再调一次。这个模式对「生成周报」这类功能仍然适用
3. **WXML 表达式不支持 `.includes()`**。多选状态要用对象 map
4. **自定义组件 `triggerEvent('tap')` 与原生 tap 冲突**，`e.detail` 会变成坐标。改名即可
5. **`db.collection().doc(id).set()` 是整文档覆盖**，会冲掉没在参数里的字段。要先 `ensureUser` 再 `update` 指定字段。**这条在网页端同样成立**——`store.js` 的 `update(uid, mutator)` 就是按这个教训设计的：mutator 拿到完整 doc 再改，而不是传一个 patch 进去

**【事实】** 还留着一条有用的经验：**云端 AI 网关的最大价值不是省事，是密钥不进代码库**。网页端没有这个选项，所以 `DEEPSEEK_API_KEY` 只能从环境变量读，且 `.env` 不能进版本库。
