# 03 · 记忆系统

> 记忆是陪伴类产品里被反复验证的唯一留存信号，也是第一大差评来源。
> 这一册讲清楚：该记什么、怎么存、怎么取、怎么忘，以及三个 bot 之间怎么隔离。

---

## 一、先定分层，再谈实现

**【事实】** 生产级 agent 的记忆不是「一个更长的上下文窗口」，而是四层不同寿命的存储：

| 层 | 寿命 | 内容 | 我们的对应 |
|---|---|---|---|
| Conversation（上下文） | 单次请求 | 当前这轮的 system + 消息 | `turn/context.js` 组装的那一份 |
| Session（会话） | 分钟到小时 | 本次任务/话题的状态 | 现有实现里缺，**待补** |
| User（用户） | 长期 | 关于这个人的稳定事实、偏好 | `memories` 集合 |
| Organizational（组织） | 长期 | 跨用户的公共知识 | 不需要 |

**【判断】** 我们现在的实现只有「上下文」和「用户」两层，中间缺 session 层。后果：一场连续对话里的临时状态（「他刚才说在准备面试」）只能靠上下文窗口维持，一旦超过窗口就丢。P0 阶段可接受，因为单次会话通常不超过 12 条历史。

---

## 二、为什么不能「全都记住」

**【事实】** 上下文不是免费的：

- 全量历史重放的成本随轮数线性增长，40 轮之后 token 数早已不合理
- Stanford NLP 的「Lost in the Middle」研究证明：相关信息落在长上下文中部时，检索准确率显著下降
- 记忆层抽取出持久事实、只取少数相关的，可以把每次检索压到 7,000 token 以内（对比全上下文方案的 25,000+），同时基准分数更高

**【判断】** 对归岸更重要的一条：**记住一切会让「朋友感」消失**。真朋友不记得你说的每句话，他记得重要的那几件。所以「忘掉大部分」不是工程妥协，是产品要求。

---

## 三、记什么：四类事实

**【判断】** 抽取时只收这四类，其余全部丢弃：

| 类型 | 例子 | 为什么值得记 |
|---|---|---|
| `preference` | 喜欢喝冰美式、讨厌被叫「您」 | 下次不用重复说 |
| `fact` | 在做毕业设计、养了只猫叫煤球 | 构成对话的具体质感 |
| `relation` | 跟室友关系紧张、妈妈在住院 | 情绪事件的背景 |
| `goal` / `event` | 想考研、下周三答辩 | 后续跟进的自然入口 |

**明确不收的**：一次性的情绪状态（「今天很烦」）、对 AI 的评价（「你真好」）、对话元信息（「刚打开页面」）。

**【判断】** 第二条尤其重要。如果把「你真好」写进记忆，下一轮模型会去讨好，因为它记得用户喜欢被夸。

### 3.1 两级抽取

**【判断】** 现有实现是规则 + 模型两级：

1. `memory/extract-rule.js`：正则模板抓高置信事实（「我妈…」「我在…上班」）
2. 模型异步抽取：规则没抓到的，每 20 轮搭车一次

为什么不全部交给模型：**成本和延迟**。规则层零成本、零延迟，能覆盖最高频的几种表达；模型层兜住长尾。

为什么不全部用规则：中文表达太发散，「最近在弄毕业的事」这种规则抓不到。

### 3.2 置信度与待确认区

**【事实】** 成熟方案会给抽取结果设置信度阈值：高置信直接入库，低置信进入待确认区，经后续交互验证后再转正。理由是**用户随口一句不应直接变成长期偏好**。

**【判断】** 我们暂未实现待确认区，这是一个已知缺口。最小可行做法：规则抽取的进正式库，模型抽取的标 `confidence: 0.6`，只在召回时降权，不参与「主动提起」。

## 四、怎么存：三个 bot 的隔离

### 4.1 数据模型

**【判断】** 现有集合设计：

```javascript
// memories
{
  _id, uid, botId,           // botId 是隔离键，必须有值
  kind,                      // preference | fact | relation | goal | event
  text,                      // 一句自然语言，不是键值对
  confidence,                // 0-1
  createdAt, lastUsedAt,
  useCount
}
```

关键点：**`botId` 没有默认值，缺失就抛错**。同理 `listMemories(uid, botId)` 的第二个参数不给默认值。

**【事实】** 网页端的实现还多走了一步：`server/store.js` 里**根本没有**「查这个人的所有记忆」这个方法。不是约定不要用，是物理上没有这条路。这比写注释提醒可靠——注释会被后来者绕过，不存在的方法不会。

**【事实】** 为什么这点值得单独强调：见岸的代码里有一个写法 `findPersona(id) || PERSONAS[0]`——找不到就静默落到第一个人格。在单人格产品里这是容错，在三个 bot 的产品里，**这就是串味的入口**。

**【判断】** 一个通用规律：**多实体系统里，任何「找不到就用默认值」的兜底，最终都会变成数据泄漏路径。**

### 4.2 要不要共享「用户基本档案」

**【判断】** 现在不共享。理由：

- 共享档案会让三个 bot 都知道同一件事，破坏「三个独立朋友」的设定
- 法规对跨场景使用个人信息有更严要求

**【判断】但有一个例外值得考虑**：安全信息（如「曾表达过自伤」）必须跨 bot 共享。否则用户可以换个 bot 继续说，而新 bot 一无所知。这属于**安全优先于产品设定**的场景，和危机链路不走模型是同一个原则。

**【待验证】** 跨 bot 共享安全标记会不会让用户感到被监视。可能需要在首次使用时明确告知。

## 五、怎么取：召回与预算

### 5.1 多信号召回

**【事实】** 单一向量检索会漏掉专有名词和时效信息。成熟做法是语义向量、关键词（BM25）、实体链接、时效衰减并行打分后融合排序。基准数据显示多信号融合把长对话记忆准确率从 71.4 提升到 92.5。

**【判断】** 我们的规模远小于这个量级（单用户单 bot 通常几十条记忆），用向量库是过度设计。P0 采用简单规则打分，见 `memory/rank.js`：

```
score = 关键词命中权重
      + 类型权重（relation > goal > fact > preference）
      + 时效加权（近 30 天 +，超过 90 天 −）
      + 使用次数微调
```

### 5.2 上下文预算

**【事实】** 记忆注入应设固定 token 上限，通常占总上下文的 10%–20%，按相关性截断。预算机制防止记忆挤占系统指令空间，也让成本可预测。

**【判断】** 我们的做法：最多注入 5 条记忆，每条不超过 40 字，总上限约 200 字。理由不是 token 成本，是**人格一致性**——记忆塞太多，模型会变成在念档案。

### 5.3 防幻觉的硬约束

**【判断】** 这是踩过的坑：模型会把「记忆里有」理解成「可以主动提起」，然后编造细节。

现有两道防线：

1. 记忆块渲染时明确写「以下是你记得的事，**不要编造没写在这里的内容**」
2. 示例里禁止出现「你上次说」这类指涉历史的话——记忆为空时它会直接编

**【判断】** 更好的做法（未实现）：在 `turn/context.js` 里给记忆加来源标记，只允许模型引用带 id 的记忆条目，输出后校验引用的 id 是否存在。

## 六、怎么忘：三种策略不能混用

**【事实】** 遗忘有四类策略，各解决一类问题，不能互相替代：

| 策略 | 解决什么 | 我们的状态 |
|---|---|---|
| **按时间衰减** | 噪音（旧的不重要） | 未实现 |
| **按最近使用** | 噪音 | 部分（`lastUsedAt`） |
| **按重要性** | 事实（重要的旧事也要留） | 部分（类型权重） |
| **按冲突取代** | 事实（新信息覆盖旧信息） | **未实现，是缺口** |

### 6.1 衰减不等于删除

**【事实】** 成熟的记忆层把「衰减」做成检索时的重排，不是删除：最近访问的记忆最多 1.5 倍加权，长期未用的降到 0.3 倍，但**仍然留在库里**，真正最匹配时还能浮上来。这和「存储强度 vs 检索强度」的认知模型一致。

**【判断】** 我倾向采用这个思路而不是 TTL 硬删。理由：陪伴产品里「三年前他提过一次的事」突然被想起来，是最强的信任建立时刻。硬删会永久失去这个机会。

### 6.2 冲突取代是必须补的

**【判断】** 现状：用户说「我换工作了」，旧记忆「在某公司上班」仍然会在召回时出现，模型可能同时提到两个，或者提到错的那个。

修法（按 mem0 的四操作模型）：

```
新事实进来时，先找语义相近的旧记忆：
- 没有相近的 → ADD
- 相近且互补 → UPDATE（合并）
- 相近且矛盾 → DELETE 旧的 + ADD 新的
- 相近且无新增 → NOOP
```

**【判断】** 争议点：矛盾时是「删掉旧的」还是「标记失效但保留」。我倾向**标记失效保留**，理由是可审计——用户问「你为什么记得这个」时能解释。但实现成本更高。P0 可以先硬删。

## 七、隐私与删除权

**【事实】** 《个人信息保护法》框架下，用户对自己被存储的画像与交互历史有查询、更正、删除的权利。工程上必须支持按用户一键清除全量副本，并留存删除审计日志。

**【判断】** 现有缺口：**没有做「清除我的记忆」入口**。这是一个 P0 级缺失，不只是合规问题——陪伴产品里用户会想看「它到底记得我什么」，这个入口本身就是信任的一部分。

建议的实现顺序：

1. `pages/memory` 页面：列出当前 bot 记得的所有条目，可单条删除
2. 单条删除后立即重建 system prompt，验证下一轮不再出现
3. 「清空全部」按钮，二次确认
4. 服务端记录删除操作（谁在什么时候删了什么类型的条目，不记内容）

---

## 八、待验证

**【待验证】**

1. 抽取准确率没有测过——不知道规则层和模型层各自贡献多少
2. 「主动提起记忆」的频率多少合适。提太多像监视，提太少像失忆。现在完全靠 prompt 里的软约束
3. 用户对「被记住」的真实反应。可能有人觉得贴心，有人觉得冒犯，这个分界线在哪不清楚
